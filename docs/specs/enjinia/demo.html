Conceptual design

Sheet 2 of 5

Pure concepts. No tables, no HTTP, no language. The model states what must stay true. The model checker tries to break it under crashes and retries.

Model and invariants

\* key of an event: (partner, event_id)
VARIABLES accepted, applied, state
state[k] ∈ {received, claimed, applied}

\* INV-1 NoDoubleApply   (BR-2, FR-4)
∀ k : Count(applied, k) ≤ 1

\* INV-2 NoLoss          (BR-1)
k ∈ accepted  ⇒  ◇ (k ∈ applied)

\* INV-3 OnlySigned      (FR-2)
k ∈ accepted  ⇒  Valid(sig(k))

\* INV-4 PerOrderOrder   (G-1)
seq(a) < seq(b) ∧ order(a)=order(b)
  ⇒ applyTime(a) < applyTime(b)

Verification tier per invariant

InvariantTierWhy
INV-1formalMoney. Crash and retry interleavings.
INV-2formalLiveness under worker crash.
INV-3exampleStateless check.
INV-4propertyPure ordering logic.

Capacity estimate

λ = 2,000/s · s = 4 ms · c = 12 workers
offered load = λ·s = 8 · ρ = 8/12 = 0.67

Estimate, not a benchmark. Service time is a guess. Stage 4 measures it.

Model check, run 1: INV-1 violated (CE-1). received → claimed(w1) → apply(w1) → crash(w1) → reclaim(w2) → apply(w2) A worker applies the effect, then crashes before it marks the event done. A second worker applies it again. Concept fix. Apply and mark are one atomic step. Run 2: no violation in 1.2 M states.
Loopback L1 to requirements. The model needs to know how partners retry. If a partner resends after a slow ack, the same event arrives twice with no crash at all. The requirements do not say how long resends can occur. You answered: partners retry for up to 24 h. Result: new requirement FR-4, requirements rev B.

Components

ComponentOwnsRealizes
ingressVerify signature, insert into inbox, ackINV-3
inboxTable, unique key (partner, event_id)INV-1, INV-2
claim-loopFOR UPDATE SKIP LOCKED, per-order lockINV-2, INV-4
applierEffect + status in one transactionINV-1 (CE-1 fix)
replay-cliReset status by time rangeFR-3

Sequence: happy path

  1. Partner sends POST /webhooks/acme.
  2. ingress verifies the signature.
  3. ingress inserts into inbox. A duplicate key is a no-op.
  4. ingress returns 202. The ack is durable from here.
  5. claim-loop claims the oldest row for that order.
  6. applier writes the order and marks the row applied in one transaction.

Decision log

ADR-1Postgres inbox over Kafka. TR-1 forbids a new broker. Load is 8 erlangs, well inside one primary.
ADR-2Unique key for dedupe over a Redis set. One store, one transaction, so INV-1 holds by construction.

S2 applyExactly-once apply. Poller turned off.
S3 hardenBackpressure and metrics for NFR-1 and NFR-2.
